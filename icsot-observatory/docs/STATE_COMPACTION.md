# Manual working-state compaction

The `Compact one working-state snapshot` Actions workflow is manual-only. It targets one existing authenticated snapshot, never collects from the source or fetches Git, and does not use a source PAT. The workflow uses the same `persistent-collection` queue as recurring collection and does not cancel a running collection. Select one numeric repository ID and its exact bound slug, review the destination and canonical current pointer SHA-256, and supply those values at dispatch. The optional encrypted index SHA-256 provides an additional predecessor pin. A changed pointer or mismatched ID, slug, destination, root or key prevents compaction; inspect the current selector and deliberately review a new dispatch instead of retrying a stale pin.

The runner uses the existing operational `COLLECTOR_STATE_PRIVATE_KEY` secret and `keys/working-state-rsa-public.pem`. It authenticates the selected index and restores the working root under its bound `/tmp/icsot-persistent-state/<id>` path, then compacts eligible whole immutable-part closures into a new generation. The planner selects the smallest eligible whole closures first within its bounds; this heuristic does not guarantee optimal savings. Mutable files and parts that cannot be safely combined remain represented. The original source observation timestamps, file contents and modes, proof outbox and old assets are preserved. A completed compaction creates a new generation with its own maintenance snapshot start and seal UTC; its authenticated maintenance context identifies the predecessor snapshot interval and context SHA separately from source observation times. No evidence capsules or owner key are involved.

The hosted bounds are 2 GiB restored logical state, 512 MiB selected input, 128 selected parts, 544 MiB ciphertext upload including index overhead, at least 16 fewer referenced parts, and 30 minutes for compaction within a 60-minute job. The time bound is checked between operations; a blocked individual network operation may exceed it. Before preparing or uploading new assets, the store checks free disk for frozen ciphertexts plus the larger of index preparation/verification scratch or a second complete reconstruction with old-part and group scratch. The index allowance includes simultaneous plaintext and encrypted scratch even when frozen capture must copy instead of hardlink; the candidate plaintext size must fit its admitted bound. Preparation index files are removed after frozen capture, and downloaded index files after authentication and comparison, before reconstruction. The frozen encrypted index remains available through uploads and fresh remote verification. Destination API headroom is checked before uploads. The initial restore has its own disk preflight. These are admission estimates, not a throughput guarantee.

Before changing the authoritative selector, the store freshly downloads and authenticates the new remote index and every referenced part, reconstructs the complete state separately, verifies file hashes and modes, and compares-and-swaps the pointer. If the savings threshold is not met, `no_op` makes no publication. Uploaded assets from an interrupted or rejected attempt can remain unreferenced; old assets are not deleted. There is no durable compaction retry journal and no automatic regeneration or rollback. An operator may explicitly retry against the same reviewed predecessor pin after checking the actual selector; a fresh attempt creates a fresh generation and may leave additional bounded unreferenced assets. An error before the compare-and-swap cannot publish the candidate, but an ambiguous compare-and-swap or a failure after it can leave the current selector advanced. Check the actual authoritative pointer before a retry or recovery; do not automatically roll back or assume an error means the old pointer is still current.

The fresh remote reconstruction verifies the complete logical working-state files and their metadata. It preserves the MAIN evidence dependency references but does not audit availability of every MAIN evidence payload; `verification_scope` identifies this as `working_state_files_only`.

The bounded metadata artifact reports the selected identities, code and plan hashes, old/new pointer and encrypted-index hashes, restored bytes, referenced part counts and ciphertext bytes, input and upload totals, API request counts, predecessor snapshot and maintenance snapshot times, timing and full remote reconstruction status. `baseline_evidence_bytes` and `new_observations` are zero. `publication` is `confirmed`, `unchanged_at_check`, or `unknown`. After a reported failure the runner makes one best-effort metadata-only selector inspection, with no retry or rollback; it reports the observed pointer and index digests when available. It confirms publication only when the observed pointer exactly matches the candidate created by that attempt. The report labels this confirmation `pointer_digest_only`: the readback does not reverify slug binding, outbox or assets at that head. The complete remote reconstruction gate ran before the candidate compare-and-swap. The inspection is a point-in-time observation; later writers can change the selector. A failed inspection reports a safe category and leaves publication unknown. Artifact retention is seven days and is not the evidence store. A hard timeout or failure before report creation may leave no outcome artifact. Recovery remains an explicit operator action against the actual selector and retained generations.

The authenticated encrypted state index is the diagnostic manifest: it contains full SHA-256 hashes, byte counts and part mappings for the logical files and parts. Compare the full recorded hashes when investigating; short hash prefixes are only display aids. Selected integrity failures can report a bounded verifier stage, safe file or part identifier, field and full expected/actual SHA-256 values or byte counts in the metadata artifact. Other errors remain categorized without raw exception text.
